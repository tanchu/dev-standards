# Общие правила разработки (Next.js, @tanchu/agent-rules)

Общие для всех проектов на Next.js правила. Правила конкретного проекта — в его `AGENTS.md`;
если они противоречат этим, прав `AGENTS.md` проекта.

## Стек

Next.js (App Router) + React + TypeScript, Tailwind CSS v4 или CSS Modules, next-intl,
Playwright, pnpm. Общие конфиги — пакеты `@tanchu/eslint-config`, `@tanchu/stylelint-config`,
`@tanchu/tsconfig`; общий CI — `tanchu/dev-standards/.github/workflows/next-ci.yml`.
Сервер, порты, домены и деплой — приватный репозиторий `tanchu/infra`.

## Официальные правила и скиллы вендоров

Правила вендоров не копируем сюда — подключаем как живые источники, они обновляются сами.
Если наши правила с ними расходятся, прав этот файл и `AGENTS.md` проекта.

- **Next.js — документация в пакете** (Vercel). С Next 16.3 полная документация лежит в
  `node_modules/next/dist/docs/`, а `next dev` ведёт блок `<!-- BEGIN:nextjs-agent-rules -->`
  в `AGENTS.md`. Блок не удаляй и не переноси внутрь него свои правила (его перезаписывают).
  Перед кодом с API Next (кэш, маршруты, `next.config`, серверные функции) прочитай
  соответствующий раздел этих docs: они про установленную версию, а не про ту, что в памяти.
- **Modern Web Guidance** (Google Chrome, вместе с Firefox, Edge и MDN). Перед UI, CSS-раскладкой
  и анимацией, формами, диалогами и поповерами, датами, производительностью и доступностью —
  `search` → `retrieve` нужного руководства и следуй ему с учётом нашего browserslist.
  Плагин Claude Code: `modern-web-guidance@claude-plugins-official`.
- **Vercel agent-skills**: `react-best-practices` (производительность React и Next:
  водопады запросов, бандл, рендер — перед оптимизацией и ревью) и `web-design-guidelines`
  (ревью UI: доступность, формы, анимации, картинки — перед тем как сдать страницу).
  Установка: `npx skills add https://github.com/vercel-labs/agent-skills` или плагин Vercel
  для Claude Code.
- **Cloudflare skills** — только если проект использует Workers, R2, KV и т. п.
  (`npx skills add https://github.com/cloudflare/skills`). Для сайтов за Cloudflare как CDN
  достаточно `tanchu/infra`.

## Версии пакетов

Ставь последнюю совместимую версию (`npm view pkg version` перед установкой), а не версию
из памяти. Если последняя ломает peer-зависимость — фиксируй совместимую и пиши в коммите почему.

## CI и выпуск

- Проверки идут на каждом PR и прямо перед выпуском (деплой по тегу `v*`, публикация в npm).
  На push в `main` не запускаются: код попадает в `main` только через PR с зелёным CI.
- Branch protection на бесплатном плане нет: мержи PR только после зелёного CI.
- Выпуск — тег `v*` на коммите из `main`; деплой сам прогоняет все проверки и выкладывает
  ровно этот коммит. Откат — Re-run деплоя у старого тега.

## Lint и typecheck — только при изменении кода

Если в `git diff --name-only` нет `.ts`/`.tsx`/`.css`, локально lint и typecheck не гоняй:
CI всё равно проверит.

## Структура

Next.js не навязывает схему ([Project structure](node_modules/next/dist/docs/01-app/01-getting-started/02-project-structure.md)),
поэтому наша одна на все проекты: общий код — в слоях `src/`, код одной страницы — рядом
с ней в `_components/`. Структуру проверяет ESLint (`@tanchu/eslint-config`).

```
src/
  app/                    ← маршруты и код, нужный одной странице
    [locale]/
      layout.tsx
      (home)/             ← главная — в группе маршрутов: URL тот же, своя `_components`
        page.tsx
        _components/
      about/
        page.tsx
        _components/      ← только /about: компоненты, хуки, content.ts / content.en.ts
  components/             ← нужное двум и более страницам: layout/, ui/, seo/, по темам
  lib/                    ← логика без React: данные, API, утилиты
  config/  i18n/          ← настройки и переводы
```

- **Страница владеет своей `_components/`** (App Router не считает папку с `_` маршрутом):
  её модули импортирует только эта страница. Понадобился второй — переноси в
  `src/components/` (`src/lib/`) и импортируй оттуда на обеих страницах
  (`@tanchu/no-cross-route-imports`). Дочерняя страница тоже не берёт из `_components`
  родителя.
- **Нет общей `_components` над страницами.** У `[locale]/` (и любой папки со вложенными
  страницами) своя `_components` — только для её `layout`, `not-found` и т. п. Главную клади
  в группу `(home)/`; шапку, подвал и меню — в `src/components/layout/`.
- **Подпапки в `_components` — только для частей этой же страницы.** Подпапка с именем
  другой страницы (`_components/basic-wardrobe/` у главной) значит, что код лежит не там.
- **Слои зависят сверху вниз**: `app` → `components` → `lib` → `config`/`i18n`.
  `components` не импортирует `app`, `lib` не импортирует `components` и `app`
  (`boundaries/dependencies`).
- **Импорты только через `@/`**, в том числе соседних файлов: `@/app/[locale]/about/_components/content.en`,
  не `./content.en`. По пути сразу видно, откуда модуль; `eslint --fix` переписывает
  относительные пути сам. Исключение — файлы вне `src/` (`messages/*.json`, `public/`).
- Один TSX-компонент на файл; хелперы, типы и константы могут жить рядом с ним.
- Компонент длиннее 300 строк — сигнал разбить (ESLint предупреждает). Если разбивать
  нет смысла — комментарий в начале файла почему.
- По умолчанию Server Components; `"use client"` — только когда нужны хуки, обработчики,
  браузерные API, и как можно ниже по дереву.
- Компоненты — именованные экспорты (`export function X`); `export default` — только
  файлы Next (`page.tsx`, `layout.tsx` и т. п.).
- React-типы импортируй напрямую: `import type { ReactNode } from 'react'`, не `React.ReactNode`.
- Избегай лишних `useEffect`: вычисляй состояние при рендере, данные получай на сервере.

## Стили

- **Tailwind CSS v4**: только классы из шкалы (`gap-y-15`, не `gap-y-[60px]`), брейкпоинты
  только в rem — именованные из `@theme` или `min-[NNrem]:`, размер шрифта только чётный.
  Tailwind сортирует брейкпоинты в px и rem не по значению, поэтому px-брейкпоинт может
  перебить rem-брейкпоинт. Классы в константах называй `*_CLASS`, `*_CLASSES`, `*_SIZE`,
  `*_COLOR`, `*_STYLE(S)` — так их проверяет линтер. Всё это проверяет ESLint и часть
  исправляет `eslint --fix`.
- **Без Tailwind** (обычный CSS / CSS Modules): имена классов по BEM в kebab-case —
  `block`, `block__element`, `block--modifier`; проверяет stylelint.
- **Цвета — только OKLCH** (`oklch(39.45% 0.0367 150.51)`, прозрачность `oklch(… / 50%)`),
  через токены `@theme`/переменные; не hex/rgb/hsl и не прямо в классе (`bg-[#…]`).
- **Единицы**: размер шрифта, отступы и брейкпоинты — `rem`; межбуквенный интервал — `em`;
  межстрочный — без единиц; `px` — для рамок, теней и «волосяных» деталей.
- Без `!important`.

### Токены темы — только с согласия владельца

- У каждого проекта свой набор токенов и переменных темы: цвета, шрифты, размеры текста,
  виды заголовков, кнопки, брейкпоинты. Они живут в CSS — в `@theme` и `@utility` файла темы
  (в проектах на Tailwind — `src/app/theme.css`), а не в TS-константах: компоненты ссылаются
  на них классами (`text-body`, `heading-section`, `btn-accent`) или `var(--…)`.
- Размер текста — только из токенов: не `text-[0.875rem]`, `text-[clamp(…)]` и не
  `font-size: 14px`, а `text-small` / `font-size: var(--text-small)`. Проверяют ESLint и stylelint.
- **Новый токен, переменную темы, вид заголовка или кнопки без спроса не вводи.** Сначала
  возьми ближайший из имеющихся. Если ни один не подходит — остановись и спроси владельца:
  что за элемент, какие токены рассматривал и почему они не подходят, какое значение
  предлагаешь. Менять значения существующих токенов — тоже только с согласия.

## Браузеры

Поддерживаемые браузеры — `@tanchu/browserslist-config` (`"browserslist": ["extends
@tanchu/browserslist-config"]` в `package.json`): минимум Tailwind v4 — Chrome/Edge 111,
Safari 16.4 — с мобильными версиями; Firefox — от 115 (ESR для Windows 7/8.1).
API, которого нет хотя бы в одном браузере из списка, включай только с проверкой поддержки
и рабочим поведением без него (полифилл, подгружаемый только там, где нужен, или упрощённый
вариант). `eslint-plugin-compat` ловит API из своей базы; совсем новые API он не знает —
проверку поддержки для них пиши сам.

## Доступность

WCAG 2.2 AA: строгий `jsx-a11y` в ESLint, axe в E2E-тестах. Текущий пункт меню —
`aria-current="page"` и не только цветом.

## Тесты

- E2E — `tests/e2e/` (Playwright), компонентные — рядом с компонентом (`*.spec.tsx`).
- Page Object для сложных страниц; локаторы — `getByRole`/`getByText`/`getByLabel`.
  `data-testid` в нотации BEM (`cookie-banner__accept`) — только там, где текст зависит от
  языка, и только когда он нужен тесту. В продакшен-сборке `data-testid` вырезается
  (`compiler.reactRemoveProperties`).
- Без `page.waitForTimeout()`: жди элементы, текст, ответы сети; web-first утверждения.
- Внешние API в E2E — заглушки (`page.route()` или локальный stub-сервер).
- Эталон вычисленных стилей (`computed-styles.spec.ts`) ловит сдвиги вёрстки дешевле
  скриншотов. Рефакторинг должен проходить без изменений эталона; намеренная правка
  вёрстки — `--update-snapshots` и проверка diff в PR.
