# Общие правила бэкенда (Cloudflare Workers, Node.js, @tanchu/agent-rules)

Общие для бэкенд-проектов правила: Cloudflare Worker и сервис на Node.js. Правила конкретного
проекта (боты, внешние API, данные, деплой) — в его `AGENTS.md`; если они противоречат этим,
прав `AGENTS.md` проекта.

## Стек

TypeScript в строгом режиме, pnpm. Worker — wrangler (`wrangler.jsonc`), типы среды из
`wrangler types`. Node — актуальная LTS (22/24), ESM, TypeScript запускается напрямую
(type stripping, без сборки). Общие конфиги — `@tanchu/tsconfig/worker.json` и
`@tanchu/tsconfig/node.json`, `defineBackendConfig` из `@tanchu/eslint-config/backend`;
общий CI — `tanchu/dev-standards/.github/workflows/next-ci.yml` с `e2e: false`.

## Официальные правила и скиллы вендоров

Не копируем сюда — подключаем как живые источники. Если наши правила с ними расходятся, прав
этот файл и `AGENTS.md` проекта.

- **Cloudflare skills** (`npx skills add https://github.com/cloudflare/skills`, в Claude Code —
  плагин `cloudflare@cloudflare`). Перед кодом Worker — `workers-best-practices`; деплой,
  биндинги, KV/R2/D1/Queues — `wrangler`; Durable Objects — `durable-objects`. Скиллы берут
  ответы из текущей документации Cloudflare — доверяй ей, а не памяти: API меняются быстро.
- **Node.js** — документация установленной версии (`node -v`, затем nodejs.org/docs/vX/api/).
  Не используй API, помеченные Experimental, без записи в `AGENTS.md` проекта.

## Типы: без лазеек

Строгость проверяют tsconfig и ESLint; обходить их нельзя. Нет корректного типа — значит,
не хватает проверки или схемы, а не приведения.

- Запрещены `any`, `as X` (кроме `as const`), non-null `!`, `@ts-ignore`, `@ts-nocheck`,
  `eslint-disable` без причины. `@ts-expect-error` — только временно, с описанием и задачей
  (см. «Переход на строгий режим»).
- **Данные снаружи — `unknown`, пока не проверены.** Тело запроса, ответ внешнего API,
  вебхук, сообщение из очереди, строка из БД, JSON из KV — разбираются схемой (zod/valibot —
  что уже есть в проекте) на границе модуля. Внутри — только проверенные типы.
- Схема — источник типа: `type Order = z.infer<typeof OrderSchema>`, а не тип и схема
  отдельно.
- Экспортируемые функции — с явным типом результата.
- Объединения (`status: 'new' | 'paid'`) обрабатывай исчерпывающе: `switch` без `default`,
  ESLint покажет забытый вариант.
- Не меняй tsconfig, правила ESLint и `@tanchu/*`-пресеты, чтобы ошибки исчезли. Если правило
  мешает по делу — остановись и опиши случай.

## Ошибки

- `catch (error)` получает `unknown`: сужай (`error instanceof Error`) или заворачивай —
  `throw new Error('Не удалось сохранить заказ', { cause: error })`.
- Пустой `catch` запрещён. Глотать ошибку можно только намеренно: комментарий почему и лог.
- Бросай только `Error` (и его подклассы), не строки и не объекты.
- Лог ошибки — с контекстом (что делали, id сущности), без секретов и персональных данных.
- Ответ клиенту — без стека и внутренних сообщений; код статуса по смыслу (400 — плохой
  ввод, 401/403, 404, 409, 422, 5xx — только наши сбои).

## Асинхронность

- Каждый промис или ожидается (`await`), или явно передан дальше: в Worker фоновая работа —
  `ctx.waitUntil(promise)`, в Node — очередь/планировщик с обработкой ошибок. `void promise`
  без обработки ошибки запрещён.
- Внешние запросы — с таймаутом (`AbortSignal.timeout(ms)`) и понятной реакцией на отказ.
- Повторы — только для идемпотентных операций, с ограничением числа попыток.

## Cloudflare Worker

- **Нет глобального изменяемого состояния**: изолят переиспользуется между запросами и
  пользователями. Состояние — в KV/D1/R2/Durable Objects.
- Переменные и секреты — из `env` (биндинги), не `process.env`. Тип `Env` генерирует
  `wrangler types` (файл `worker-configuration.d.ts`, руками не правится; свои типы —
  отдельным файлом через `Cloudflare.Env`). После правки `wrangler.jsonc` — перегенерируй.
- Секреты — `wrangler secret put`, не в `wrangler.jsonc` и не в `vars`.
- Тело запроса и ответа читается один раз; большие ответы — потоком, без буферизации.
- Node-API в Worker — только с флагом `nodejs_compat` и импортом `node:*`.
- Помни о лимитах (CPU-время, число подзапросов, размер тела): тяжёлое — в Queues/Workflows.
- Тесты — `@cloudflare/vitest-pool-workers` (настоящий рантайм), локально — `wrangler dev`.

## Сервис на Node.js

- ESM, встроенные модули только как `node:fs`, `node:path`.
- TypeScript без сборки: только стираемый синтаксис (`erasableSyntaxOnly`) — без `enum`,
  `namespace`, параметров-свойств конструктора; вместо `enum` — объединение строк или
  `as const`-объект. Импорты относительных файлов — с расширением `.ts`.
- `process.env` читается в одном модуле (`src/config/env.ts`) через схему; остальной код
  получает типизированный config. Без нужной переменной сервис падает при старте, а не
  в середине работы.
- Корректная остановка: на `SIGTERM`/`SIGINT` перестать принимать запросы, дождаться
  текущих, закрыть соединения.
- В обработчиках — без синхронного I/O (`readFileSync` и т. п.).
- Логи — структурированные (JSON-строка с `level`, `msg`, контекстом), `console.info/warn/error`
  или логгер проекта; `console.log` — нет.

## Структура

```
src/
  index.ts        ← точка входа: Worker handler или запуск сервера, только сборка частей
  routes/         ← HTTP/вебхуки: разбор входа схемой, вызов логики, ответ
  domain/         ← логика без транспорта и внешних SDK
  adapters/       ← внешние API, БД, KV/R2: здесь же схемы их ответов
  config/         ← env и константы
```

Слои зависят сверху вниз: `routes` → `domain` → `adapters`/`config`; `domain` не знает о
HTTP и о конкретном SDK. Общий код нескольких сервисов монорепо — в пакете `packages/*`,
не копией.

## Как работать агенту

- **Маленькие изменения.** Одна задача — один модуль или одна сквозная правка, diff в
  пределах нескольких сотен строк. Большую задачу сначала разбей и покажи план.
- **Не подгоняй проверки под код**: не ослабляй типы, правила, тесты и их ожидания, чтобы
  стало зелёным. Тест упал — сначала выясни, кто прав: код или тест.
- **Не угадывай.** Неизвестна форма данных внешнего API — найди документацию или пример
  ответа; нет их — спроси. Не выдумывай поля.
- Перед сдачей: `pnpm lint`, `pnpm typecheck`, `pnpm test` в затронутых пакетах. В отчёте —
  что проверено, что нет и почему.
- Новые зависимости — только с причиной в коммите; последняя версия (`npm view pkg version`).

## Переход на строгий режим

Когда строгие настройки включаются в существующий код и ошибок сотни:

1. Отдельный PR — только конфиги (tsconfig, ESLint, CI), без правок кода.
2. Текущие ошибки фиксируются как исходный долг: `@ts-expect-error TODO(strict): …` и
   `eslint-disable-next-line <правило> -- TODO(strict)` расставляются скриптом, а не
   вручную, чтобы CI стал зелёным и ловил новые ошибки.
3. Дальше — по одному модулю на PR, начиная с границ (входящие запросы, внешние API,
   env): схема на границе убирает большую часть ошибок внутри. Каждый PR уменьшает число
   `TODO(strict)` (`grep -rc 'TODO(strict)' src`) и не добавляет новых.
4. Нельзя: массово заменять ошибки на `as`/`any`/`!`, переименовывать `.js` в `.ts` без
   типов, отключать правила.

## CI и выпуск

- Проверки идут на каждом PR и прямо перед выпуском. На push в `main` не запускаются: код
  попадает в `main` только через PR с зелёным CI.
- Выпуск — тег `v*` на коммите из `main`; деплой сначала прогоняет все проверки, потом
  выкладывает ровно этот коммит. Откат — Re-run деплоя у старого тега.
- В `typecheck` Worker входит `wrangler types --check`: устаревшие типы `Env` — ошибка CI.
- Деплой Worker — `wrangler deploy` из workflow выпуска, не с локальной машины.
