# Общие правила бэкенда (@tanchu/agent-rules)

Общая часть для бэкенда на TypeScript. Её читают вместе с правилами среды: `worker.md`
(Cloudflare Worker) или `node.md` (сервис на Node.js); в монорепо с обеими средами — оба.
Правила конкретного проекта (что он делает, внешние API, данные, деплой Node) — в его
`AGENTS.md`; если они противоречат этим, прав `AGENTS.md` проекта.

## Стек

TypeScript в строгом режиме, pnpm, ESM. Общие конфиги — `@tanchu/tsconfig/worker.json` или
`@tanchu/tsconfig/node.json`, `defineBackendConfig({ runtime })` из
`@tanchu/eslint-config/backend`; общий CI — `tanchu/dev-standards/.github/workflows/next-ci.yml`
с `e2e: false`. Схемы данных — zod или valibot, что уже есть в проекте.

## Монорепо

- Код, нужный двум сервисам, — в пакете `packages/*`, не копией.
- Общий пакет не читает ни `env` Worker, ни `process.env`: настройки ему передают
  параметром. Поэтому он работает в любой среде (`"types": ["@cloudflare/workers-types"]`
  или без типов среды).
- У каждого сервиса свой `tsconfig.json` и `eslint.config.mjs` со своей средой.

## Типы: без лазеек

Строгость проверяют tsconfig и ESLint; обходить их нельзя. Нет корректного типа — значит,
не хватает проверки или схемы, а не приведения.

- Запрещены `any`, `as X` (кроме `as const`), non-null `!`, `@ts-ignore`, `@ts-nocheck`,
  `eslint-disable` без причины. `@ts-expect-error` — только временно, с описанием
  (см. «Переход на строгий режим»).
- **Данные снаружи — `unknown`, пока не проверены.** Тело запроса, ответ внешнего API,
  вебхук, сообщение из очереди, строка из БД, JSON из KV, переменные окружения —
  разбираются схемой на границе модуля. Внутри — только проверенные типы.
- Схема — источник типа: `type Order = z.infer<typeof OrderSchema>`, а не тип и схема
  отдельно.
- Экспортируемые функции — с явным типом результата.
- Объединения (`status: 'new' | 'paid'`) обрабатывай исчерпывающе: `switch` без `default`,
  ESLint покажет забытый вариант.
- Не меняй tsconfig, правила ESLint и `@tanchu/*`-пресеты, чтобы ошибки исчезли. Если правило
  мешает по делу — остановись и опиши случай.

## Внешние API и вебхуки

- **Не угадывай форму данных.** Схема ответа или вебхука — по документации API или по
  реальному примеру ответа. Нет ни того, ни другого — остановись и спроси; не выдумывай поля.
- Схема описывает только поля, которые код использует; лишние поля не ломают разбор.
- Вебхук с неизвестным типом события (новый тип апдейта, событие, которое мы не
  обрабатываем) — лог и успешный ответ, не ошибка: иначе отправитель будет повторять его.
  Ошибка разбора известного типа — лог с типом события и id, ответ 4xx/5xx по смыслу.
- Подпись или секрет вебхука проверяется до разбора тела.
- Клиент внешнего API — в `adapters/`: таймаут, разбор ответа схемой, понятная ошибка с
  `cause`. Остальной код получает проверенные данные, а не сырой `Response`.

## Секреты

- Значения секретов не попадают в репозиторий, логи, ответы клиенту и тексты ошибок.
- Где они хранятся и как читаются — в правилах среды (`worker.md`, `node.md`).
- Пример настроек для разработки (`.dev.vars.example`, `.env.example`) — без настоящих
  значений.

## Ошибки

- `catch (error)` получает `unknown`: сужай (`error instanceof Error`) или заворачивай —
  `throw new Error('Не удалось сохранить заказ', { cause: error })`.
- Пустой `catch` запрещён. Глотать ошибку можно только намеренно: комментарий почему и лог.
- Бросай только `Error` (и его подклассы), не строки и не объекты.
- Лог ошибки — с контекстом (что делали, id сущности), без секретов и персональных данных.
- Ответ клиенту — без стека и внутренних сообщений; код статуса по смыслу (400 — плохой
  ввод, 401/403, 404, 409, 422, 5xx — только наши сбои).

## Асинхронность

- Каждый промис или ожидается (`await`), или явно передан дальше (как — в правилах среды).
  `void promise` без обработки ошибки запрещён.
- Внешние запросы — с таймаутом (`AbortSignal.timeout(ms)`) и понятной реакцией на отказ.
- Повторы — только для идемпотентных операций, с ограничением числа попыток.

## Структура

```
src/
  index.ts        ← точка входа: Worker handler или запуск сервера, только сборка частей
  routes/         ← HTTP/вебхуки: разбор входа схемой, вызов логики, ответ
  domain/         ← логика без транспорта и внешних SDK
  adapters/       ← внешние API, БД, KV/R2: здесь же схемы их ответов
  config/         ← env и константы
```

Слои зависят сверху вниз: `routes` → `domain` → `adapters`/`config`; `domain` не знает о
HTTP и о конкретном SDK.

## Как работать агенту

- **Маленькие изменения.** Одна задача — один модуль или одна сквозная правка, diff в
  пределах ~300 строк. Большую задачу сначала разбей и покажи план.
- **Не подгоняй проверки под код**: не ослабляй типы, правила, тесты и их ожидания, чтобы
  стало зелёным. Тест упал — сначала выясни, кто прав: код или тест.
- Перед сдачей: `pnpm lint`, `pnpm typecheck`, `pnpm test` в затронутых пакетах. В отчёте —
  что проверено, что нет и почему.
- Новые зависимости — только с причиной в коммите; последняя версия (`npm view pkg version`).

## Переход на строгий режим

Касается проектов, где строгие настройки включаются в существующий код (переход с JS или
со слабого tsconfig) и ошибок сотни. Признак — в коде есть `TODO(strict)`.

1. Отдельный PR — только конфиги (tsconfig, ESLint, CI), без правок кода.
2. Текущие ошибки фиксируются как исходный долг скриптом, а не вручную:
   `pnpm exec tanchu-strict-baseline` (из `@tanchu/agent-rules`) ставит над каждой ошибкой
   `@ts-expect-error TODO(strict): …` или `eslint-disable-next-line <правило> -- TODO(strict)`.
   CI становится зелёным и ловит только новые ошибки. Строки, которые скрипт пометить не
   может (внутри шаблонных строк и JSX, строки с комментарием в конце), он выводит
   списком — их правят руками в том же PR.
3. Дальше — **один модуль на PR**, diff до ~300 строк. Начинай с границ: входящие запросы и
   вебхуки, ответы внешних API, env. Схема на границе убирает большую часть ошибок внутри.
4. В описании PR — сколько `TODO(strict)` было и стало в модуле. Посчитать:
   `grep -rc 'TODO(strict)' --include='*.ts' --exclude-dir=node_modules . | grep -v ':0$'`.
5. Нельзя: добавлять новые `TODO(strict)`, `as`, `any`, `!`; массово заменять ошибки
   приведениями; переименовывать `.js` в `.ts` без типов; отключать правила.

Когда `TODO(strict)` не осталось, этот раздел к проекту больше не относится.

## CI и выпуск

- Проверки идут на каждом PR и прямо перед выпуском. На push в `main` не запускаются: код
  попадает в `main` только через PR с зелёным CI.
- Выпуск — только тег `v*` на коммите из `main`: workflow выпуска сначала прогоняет все
  проверки, потом выкладывает ровно этот коммит. Push в `main` ничего не выкладывает.
  Откат — Re-run выпуска у старого тега.
- С локальной машины в прод не выкладывают.
